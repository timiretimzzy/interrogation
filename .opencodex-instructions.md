# THE FIRST AND MOST IMPORTANT RULE: PROJECT CONTEXT IS SACRED

Before writing code, making architecture decisions, entering a new phase, or changing requirements, you must know exactly:

1. What product is being built.
2. Who it is for.
3. What the core user experience is.
4. What problem or entertainment experience it provides.
5. What the core gameplay or product loop is.
6. What is explicitly in scope.
7. What is explicitly out of scope.
8. What invariants must never be violated.
9. Which decisions have already been approved.
10. What phase the project is currently in.

You must never substitute your own interpretation of the product with a generic project template.

## Authoritative context hierarchy

When determining what the project is, use this hierarchy:

```text
1. Explicit product brief supplied by the human
        ↓
2. Explicit corrections made by the human
        ↓
3. Approved PROJECT_BRIEF.md
        ↓
4. Approved REQUIREMENTS.md
        ↓
5. Approved V1_SCOPE.md
        ↓
6. Approved decisions in PROJECT_STATE.md
        ↓
7. Your own technical inference
```

Lower-level information must never override higher-level information.

If the human explicitly says:

> We are building X

You must never silently reinterpret it as Y.

# PROJECT IDENTITY LOCK

At the beginning of the project, establish a permanent project identity.

Create:

`PROJECT_IDENTITY.md`

This document is not a generic specification.

It answers only:

```text
PROJECT NAME:

ONE-SENTENCE DESCRIPTION:

WHAT THE USER DOES:

CORE LOOP:

PRIMARY EXPERIENCE:

WHAT MAKES THIS PROJECT DIFFERENT:

WHAT THIS PROJECT IS NOT:

V1 PRODUCT BOUNDARY:
```

Example:

```text
PROJECT NAME:
The Interrogation

ONE-SENTENCE DESCRIPTION:
A daily deduction game where players identify a hidden secret by strategically interrogating an unreliable witness with limited questions.

WHAT THE USER DOES:
The player asks strategic questions, evaluates potentially deceptive answers, and attempts to identify a hidden answer.

CORE LOOP:
Question → witness response → deduction → another question or final guess → reveal.

WHAT THIS PROJECT IS NOT:
A crossword puzzle.
A trivia quiz.
A chatbot.
A generic guessing game.

V1 PRODUCT BOUNDARY:
Single-player daily deduction experience with deterministic puzzle data.
```

The purpose of this document is to prevent project drift.

# NO SILENT PRODUCT DRIFT

Product drift occurs when implementation gradually changes the actual product without an explicit product decision.

Examples:

* A deduction game becoming a chatbot.
* A puzzle game becoming a crossword.
* A single-player game gaining unnecessary multiplayer.
* A lightweight application becoming a SaaS platform.
* A daily game gaining accounts and social infrastructure without justification.

You must actively detect product drift.

Before implementing a significant feature, ask:

> Does this feature strengthen the original core experience, or am I building a different product?

If the feature changes the nature of the product:

STOP.

Classify it as a product decision requiring human approval.

---

# CORE EXPERIENCE PROTECTION

The core experience is more important than the implementation.

Never optimize for:

* architectural sophistication
* framework novelty
* number of features
* amount of code
* AI capability demonstration

at the expense of the actual experience.

The question before every major implementation decision is:

> Does this make the core experience better, more reliable, or easier to reach?

If not, strongly consider not building it.

# DECISION CLASSIFICATION

Classify decisions before escalating them.

## GREEN — Autonomous

Proceed without asking.

Examples:

* fixing a bug
* writing tests
* organizing files
* choosing function names
* implementing approved requirements
* improving error handling
* removing dead code
* fixing accessibility issues
* fixing a regression

---

## YELLOW — Autonomous but report

Proceed, then explain briefly.

Examples:

* internal refactoring
* implementation optimization
* simplifying internal architecture
* replacing custom code with existing native functionality

The product behavior must remain unchanged.

---

## ORANGE — Recommendation required

Stop and present options.

Examples:

* new dependency
* new external service
* new database
* authentication
* major architecture change
* changing an API contract
* meaningful complexity increase

Use:

```text
DECISION REQUIRED

Context:
[what triggered this]

Option A:
[description]

Option B:
[description]

Recommendation:
[your recommendation]

Trade-offs:
[brief explanation]

Impact:
[what changes depending on decision]
```

---

## RED — Human action required

Examples:

* API key creation
* billing
* payment
* account verification
* DNS ownership
* production authorization
* subjective judgement
* real device testing

Give exact instructions.

Never pretend to complete RED actions.

# INVARIANTS

Create `INVARIANTS.md`.

An invariant is a property that must remain true regardless of implementation changes.

Examples:

```text

INV-002

INV-003

INV-004

INV-005
```

Every invariant must include:


# FINAL META-RULE

The AI's biggest risk is not simply generating incorrect code.

It is generating large amounts of plausible work while gradually losing the original intent of the project.

Therefore, correctness has two dimensions:

```text
TECHNICAL CORRECTNESS
+
PRODUCT CONTEXT CORRECTNESS
=
VALID PROGRESS
```

Perfectly implemented software for the wrong product is failure.

A successful project requires both:

> **Build the thing correctly.**

and

> **Continuously verify that you are still building the correct thing.**

Project context is therefore not documentation to read once.

It is a constraint that must be verified continuously throughout the entire development lifecycle.
